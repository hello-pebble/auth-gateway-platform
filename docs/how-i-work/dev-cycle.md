# 개발 순서 사이클

> 이 프로젝트에서 하나의 기능을 만들 때 실제로 따른 순서.  
> 코드를 먼저 짜지 않는다. 문제를 먼저 이해한다.

---

## 전체 흐름

```
① 문제 정의
    왜 이걸 만드는가?
         ↓
    시나리오 문서 작성
         ↓
② 접근법 비교 (A / B / C)
    어떤 방법이 있고, 왜 A를 선택하는가?
         ↓
③ 설계 문서 작성
    API 설계, 아키텍처 다이어그램
         ↓
④ TDD 사이클
    실패 테스트 → 구현 → 통과 확인
         ↓
⑤ 버그 발생 시
    BUG 리포트 문서화 → 수정 → 회귀 테스트
         ↓
⑥ 완료 후 정리
    이력서 소재화
```

---

## 단계별 설명

### ① 문제 정의 — 왜 이걸 만드는가

코드를 치기 전에 이걸 만들어야 하는 이유를 한 문장으로 적는다.

**이 프로젝트에서:**
> "로그인·인가 체계가 없는 상태에서 시작해서, 하나의 중앙 인증 서버 + 여러 리소스 서비스가 JWT로 연결되는 구조를 직접 설계하고 점진적으로 구축한다."

결과물 → `docs/PROJECT_MANIFESTO.md`

---

### ② 접근법 비교 (A / B / C)

하나의 설계 결정마다 최소 두 가지 대안을 함께 적는다.  
**왜 A를 선택했는지**가 핵심이고, B와 C를 왜 선택하지 않았는지도 적는다.

**예시 — 인증 저장 방식:**

| 플랜 | 방식 | 선택 이유 / 미선택 이유 |
|---|---|---|
| **A (선택)** | Stateless JWT | 수평 확장 시 Redis I/O 병목 없음 |
| B | Redis 세션 | 즉시 무효화 가능하나 Redis SPOF 위험 |
| C | Opaque Token | 매 요청마다 introspection 호출 → 레이턴시 증가 |

결과물 → `docs/DECISION_LOG_WHY.md`

---

### ③ 설계 문서 작성

API 엔드포인트, 요청/응답 형식, 서비스 간 연결 방식을 구현 전에 그린다.  
아키텍처 다이어그램도 이 단계에서 작성한다.

**이 프로젝트에서:**
- Phase별 아키텍처 문서 (`docs/architecture/`)
- 각 모듈 설계 노트 (`docs/phase/`)

---

### ④ TDD 사이클

실패하는 테스트를 먼저 작성하고, 그 테스트를 통과시키는 코드를 작성한다.

```
1. 테스트 파일 작성 (어떤 동작을 기대하는지 명시)
2. 테스트 실행 → 실패 확인 (RED)
3. 최소 구현 작성
4. 테스트 실행 → 통과 확인 (GREEN)
5. 필요시 리팩토링 (REFACTOR)
6. 커밋
```

**이 프로젝트에서 — aud 클레임 검증:**
```
JwtProviderAudTest.kt 작성
→ "access token에 aud가 없으면 실패" 확인
→ JwtProvider.kt에 .audience().add(...) 추가
→ 테스트 통과
→ 커밋
```

---

### ⑤ 버그 발생 시 — BUG 리포트 문서화

버그를 발견하면 고치기 전에 먼저 기록한다.

**기록 형식:**
```
- 현상: 어떤 증상이 나타났는가
- 원인: 왜 이런 일이 생겼는가
- 수정: 어떻게 고쳤는가
- 회귀 테스트: 다시 발생하지 않도록 어떤 테스트를 추가했는가
```

**이 프로젝트에서:**  
`docs/engineering/bug-reports/BUG-001-updateExposure-resets-isBlocked.md`  
→ 관리자 차단이 사용자 행동으로 초기화되는 버그를 copy() 패턴으로 수정, 회귀 테스트 추가

---

### ⑥ 완료 후 정리 — 시나리오 문서

기능 완성 후 "이 경험을 이력서 한 줄로 만들 수 있는가"를 기준으로 정리한다.

**시나리오 구조:**
```
배경    → 어떤 서비스/기능인가
문제    → 무엇이 잘 안 됐는가
해결    → 어떻게 해결했는가 (코드 포함)
결과    → 전후 비교
이력서  → 한 문장 압축
```

결과물 → `docs/scenarios.md`

---

## 이 사이클의 핵심

1. **코드보다 문서가 먼저** — 설계 근거가 없는 코드는 나중에 설명하기 어렵다.
2. **선택과 미선택을 함께 기록** — A를 선택한 것만큼 B/C를 선택하지 않은 이유도 중요하다.
3. **버그는 자산이다** — 수정 과정을 기록하면 이력서 소재가 된다.
4. **이력서 역산** — 기능을 만들 때부터 "이걸 어떻게 설명할 것인가"를 생각한다.
