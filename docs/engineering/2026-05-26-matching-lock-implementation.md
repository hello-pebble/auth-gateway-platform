# 📅 2026-05-26 개발 일지: [matching-module] 매칭 로직 분산 락(또는 DB 락) 구현 및 Race Condition 방어 코드 추가

## 1. 시작 전
- **목표**: `MatchingService`의 `rankUser` 메서드에 정렬된 락(Ordered Lock)을 적용하여 동시성 문제를 해결하고, 원자적인 매칭 성사 보장
- **배경**: 이전 설계(5/21)에 따라 두 사용자의 ID를 기반으로 한 임계 영역(Critical Section) 설정

## 2. 진행 과정

### 🚨 Case Study: 락 구현 시 발생 가능한 문제 상황
구현 단계에서 마주할 수 있는 기술적 이슈를 고려합니다.

*   **Case 5.1: 락 획득 실패 시 처리 (Timeout vs Retry)**
    *   **상황**: 특정 유저에게 매칭 요청이 폭주하여 락 대기 시간이 길어짐.
    *   **방어책**: 무한정 대기하는 대신 적절한 타임아웃(예: 3초)을 설정하고, 실패 시 "현재 요청이 많습니다. 잠시 후 다시 시도해주세요"와 같은 사용자 친화적 에러 반환.
*   **Case 5.2: 예외 발생 시 락 해제 누락 (Resource Leak)**
    *   **상황**: 매칭 로직 실행 중 예상치 못한 RuntimeException 발생.
    *   **방어책**: `try-finally` 블록을 반드시 사용하여 어떤 상황에서도 `unlock()`이 호출되도록 보장.
*   **Case 5.3: 락 범위 과다 설정 (Performance)**
    *   **상황**: 락 안에서 외부 API 호출 등 무거운 작업을 수행함.
    *   **방어책**: 락의 범위는 오직 `InMemoryMatchingStore`의 상태 변경 및 조회에만 한정하여 최소화함.

### 🛠️ 구현 내용
- [x] `UserPairLockManager` 구현: 유저 ID 쌍을 기반으로 한 `ReentrantLock` 관리자
- [x] `MatchingService.rankUser` 리팩토링:
    - 매칭 평가 로직 시작 전 `lock(userIdA, userIdB)` 획득
    - `try-finally`를 통한 안전한 해제 보장
- [x] 동시성 테스트 케이스 작성: 다수의 스레드가 동시에 서로를 선택할 때 매칭이 정확히 1번 발생하는지 검증

## 3. 마무리
- **결과**: 상호 선택 및 중복 매칭에 대한 데이터 정합성 완벽 보장. `admin-module`의 패널티 부여와 매칭 로직 간의 충돌 가능성도 락을 통해 해결됨.
