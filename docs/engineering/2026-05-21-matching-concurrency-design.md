# 📅 2026-05-21 개발 일지: [matching-module] 다중 선택으로 인한 동시성 문제 분석 및 제어 아키텍처 설계

## 1. 시작 전
- **목표**: 매칭 시스템의 핵심인 '상호 선택' 로직에서 발생할 수 있는 데이터 정합성 문제(Race Condition)를 분석하고, 이를 해결하기 위한 락(Lock) 전략 설계
- **배경**: 여러 사용자가 동시에 서로를 선택하거나, 한 명의 인기 사용자를 향해 수백 개의 선택이 몰릴 때 발생할 수 있는 매칭 누락 및 초과 생성 방어

## 2. 진행 과정

### 🚨 Case Study: 매칭 동시성 발생 문제 상황
동시성 제어가 없을 때 발생할 수 있는 치명적인 시나리오들을 정의합니다.

*   **Case 4.1: 상호 교차 선택 시 매칭 누락 (Lost Match)**
    *   **상황**: User A와 B가 서로를 1위로 생각하고 0.001초 차이로 '선택' 버튼을 누름.
    *   **문제**: 스레드 A가 B의 선택 여부를 조회할 때 스레드 B의 쓰기가 아직 완료되지 않았고, 역으로 스레드 B도 마찬가지임. 결과적으로 둘 다 서로를 선택했음에도 "상대가 나를 선택하지 않음"으로 판단하여 매칭이 성사되지 않음.
*   **Case 4.2: 한 명의 사용자에게 몰린 중복 매칭 (Double Matching)**
    *   **상황**: User A가 B를 이미 선택한 상태에서, User B가 C와 D를 추천받아 동시에 '선택'을 진행함.
    *   **문제**: 시스템은 1:1 채팅방 생성을 보장해야 하나, 찰나의 순간에 B가 C, D와 동시에 매칭 로직을 통과하여 한 유저가 여러 명과 비정상적으로 동시에 연결됨.
*   **Case 4.3: 데드락 (Deadlock)**
    *   **상황**: 두 사용자의 데이터에 락을 거는 과정에서 스레드 1은 `A -> B` 순으로, 스레드 2는 `B -> A` 순으로 락을 시도함.
    *   **문제**: 서로의 자원을 기다리며 무한 대기에 빠짐.

### 🛠️ 설계 내용: 순차 락(Ordered Locking) 전략
- **락 대상**: 매칭을 시도하는 두 유저 ID (`fromUserId`, `toUserId`)
- **해결책**: 
    1. 두 ID를 오름차순 정렬 (예: `min(A, B), max(A, B)`)하여 항상 동일한 순서로 자원에 접근. (Case 4.3 방지)
    2. 현재 인메모리 환경이므로 유저 ID별로 `ReentrantLock`을 관리하는 `LockManager` 구현 또는 `synchronized` 블록 활용.
    3. 추후 MSA 확장을 고려하여 Redis 기반 Redisson 분산 락으로 전환 가능한 인터페이스 설계.
