# Decision Log: Stateless JWT를 선택한 이유

## 1. 해결하려는 문제

서비스마다 인증 상태를 별도로 관리하면 로그인 구현과 권한 처리 방식이 중복됩니다. 또한 여러 서버가 중앙 세션 저장소를 매 요청 조회하는 구조는 저장소 가용성과 I/O 비용에 의존합니다.

이 프로젝트는 Auth가 토큰을 발급하고 각 리소스 서버가 서명을 독립적으로 검증하는 구조를 선택했습니다.

## 2. 결정

### Access Token

- JWT로 발급합니다.
- Matching, Task, Admin이 Auth의 JWKS로 검증합니다.
- 일반 API 요청에서는 Auth나 사용자 DB를 다시 조회하지 않습니다.

### Refresh Token

- 재발급 시 기존 토큰을 교체하는 Rotation 흐름을 사용합니다.
- 현재 저장소는 `ConcurrentHashMap` 기반 인메모리 구현입니다.
- 만료 시간은 토큰 자체에 포함되지만, 인메모리 저장소는 TTL 정리 기능을 제공하지 않습니다.

### Gateway

- 외부 요청 라우팅과 쿠키→Bearer 변환을 담당합니다.
- JWT 검증과 도메인 인가는 각 백엔드 서비스에 위임합니다.

## 3. 얻은 점

- 서비스가 JWT를 로컬에서 검증하므로 일반 API 요청이 중앙 세션 조회에 의존하지 않습니다.
- Auth의 발급 책임과 도메인 서비스의 인가 책임을 구분할 수 있습니다.
- 공개키를 공유해 여러 서비스가 동일한 토큰 형식을 사용할 수 있습니다.

## 4. 감수한 점

- 발급된 Access Token을 만료 전에 중앙에서 즉시 회수하기 어렵습니다.
- 권한 변경이 기존 Access Token에 즉시 반영되지 않습니다.
- 현재 Refresh Token 저장소는 재시작 시 초기화되고 다중 인스턴스 상태를 공유하지 못합니다.
- Auth가 재시작할 때 RSA 키가 새로 생성되므로 기존 토큰 검증이 실패할 수 있습니다.

## 5. 보완 방향

- Access Token 유효기간과 권한 변경 요구사항을 함께 검토합니다.
- Refresh Token 저장소 인터페이스를 유지하고 필요할 때 외부 저장소 구현으로 교체합니다.
- 운영 환경에서는 서명 키를 안전한 외부 저장소에 보관하고 회전 정책을 정의합니다.
- 성능과 확장성은 부하 테스트 결과로 검증하며 구조만으로 처리량을 단정하지 않습니다.

## 6. 아직 검증하지 않은 것

- 동시 로그인 처리량과 지연 시간
- 인스턴스 증가에 따른 처리량 변화
- 외부 상태 저장소 적용 전후의 비용
- Auth 또는 DB 장애 시 전체 사용자 흐름

이 항목들은 향후 측정 대상이며 현재 구현의 성과로 주장하지 않습니다.
