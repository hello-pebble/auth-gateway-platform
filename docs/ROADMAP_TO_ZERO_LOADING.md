# 성능·확장성 검증 로드맵

> 이 문서는 구현 완료 목록이 아니라 향후 검증 순서를 기록한 로드맵입니다. 정량 성능 목표는 기준 환경과 부하 테스트 결과를 확보한 뒤 설정합니다.

## 현재 기준선

- JWT 발급과 JWKS 제공
- 리소스 서버의 독립적인 JWT 검증
- Gateway 기반 라우팅과 쿠키→Bearer 변환
- Refresh Token 및 대기열 접근 상태의 인메모리 저장
- Matching 데이터의 인메모리 저장

현재 구조는 기능 흐름을 검증하기 위한 단계이며, 다중 인스턴스 상태 공유나 대규모 트래픽 처리를 검증한 상태는 아닙니다.

## Phase 1 — 측정 환경 확보

- k6 또는 Gatling 기반 부하 시나리오 작성
- 테스트 데이터와 실행 환경 고정
- 처리량, 오류율, p50/p95/p99 기록
- CPU, 메모리, DB 커넥션 사용량 관찰

측정 결과가 이후 기술 선택의 기준이 됩니다.

## Phase 2 — 트래픽 보호

- IP 또는 사용자 기준 Rate Limit
- 초과 요청에 대한 일관된 429 응답
- 허용량과 대기 정책을 설정값으로 분리
- 정상 요청과 비정상 반복 요청을 구분한 테스트

## Phase 3 — 상태 저장소 교체

- Refresh Token과 대기 상태의 만료 정책 정의
- 인메모리 구현과 외부 저장소 구현을 인터페이스로 분리
- 다중 인스턴스에서 상태 정합성 검증
- 외부 저장소 장애 시 동작과 복구 정책 정의

## Phase 4 — 비동기 처리 검토

Coroutines, R2DBC 또는 이벤트 기반 처리는 목표가 아니라 선택지입니다. 프로파일링을 통해 스레드 대기나 DB I/O가 실제 병목으로 확인된 경우에만 작은 범위부터 적용하고 전후 결과를 비교합니다.

## Phase 5 — 장애 격리와 운영성

- 서비스 간 호출 timeout과 오류 매핑
- 조회 요청에 한정한 retry 검토
- Trace ID와 분산 추적 도입
- 서비스별 health/readiness 기준 분리
- 장애 시나리오 기반 복구 검증

## 완료 기준

각 단계는 “기술을 적용했다”가 아니라 다음 증거를 남겼을 때 완료로 판단합니다.

- 재현 가능한 실행 명령
- 테스트 또는 부하 시나리오
- 적용 전후 측정 결과
- 실패 조건과 트레이드오프 기록
