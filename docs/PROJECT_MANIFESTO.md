# Project Manifesto: 인증에서 서비스 경계까지

## 1. 프로젝트가 답하려는 질문

> 중앙 인증 서버가 발급한 토큰을 여러 서비스가 독립적으로 검증하고, 각 서비스의 책임과 권한 경계를 유지할 수 있는가?

이 프로젝트는 OAuth2 인증 서버 구현에서 시작했습니다. 발급한 토큰을 실제 서비스가 소비하는 흐름을 확인하기 위해 Gateway, Task, Matching, Admin, Preview 모듈을 단계적으로 분리했고, 현재는 서비스 경계와 통신 방식을 검증하는 프로젝트로 확장되었습니다.

---

## 2. 현재 코드로 확인할 수 있는 사실

### 중앙 발급과 분산 검증

- Auth가 JWT를 발급하고 JWKS 엔드포인트를 제공합니다.
- Matching, Task, Admin은 Auth의 공개키로 JWT를 독립 검증합니다.
- 일반 API 요청마다 중앙 세션 저장소를 조회하지 않습니다.

### Gateway의 제한된 책임

- Gateway는 외부 요청을 대상 서비스로 라우팅합니다.
- 쿠키의 Access Token을 `Authorization: Bearer` 헤더로 변환합니다.
- Gateway는 JWT를 검증하지 않으며, 인증과 인가는 각 리소스 서버가 담당합니다.

### 서비스 간 호출

- Admin은 Matching의 내부 관리 API를 직접 호출합니다.
- 사용자 JWT를 전달하고 양쪽 서비스가 `ROLE_ADMIN`을 확인합니다.
- 현재 방식은 구현이 단순하지만, 사용자 토큰이 서비스 간 자격 증명 역할까지 담당한다는 한계가 있습니다.

### 현재 저장소 구현

- Auth 사용자 데이터는 PostgreSQL(prod) 또는 H2(dev)에 저장합니다.
- Refresh Token, 대기열 접근 상태, Matching 데이터는 인메모리 저장소를 사용합니다.
- 따라서 관련 상태는 프로세스 재시작 시 사라지고 다중 인스턴스 간 공유되지 않습니다.

---

## 3. 검증된 사실과 향후 목표의 구분

현재 저장소에는 대규모 부하 테스트 결과가 없습니다. 처리량, 지연 시간, 선형 확장성을 보장하지 않으며, Stateless JWT 구조가 실제 환경에서 어느 정도의 효과를 내는지는 별도 측정이 필요합니다.

향후 성능 검증 시에는 다음 항목을 측정합니다.

- 로그인 및 토큰 발급 처리량
- API 요청의 p50, p95, p99 지연 시간
- Auth 또는 DB 지연 시 이미 발급된 JWT를 사용하는 서비스의 동작
- 인스턴스 수 변화에 따른 처리량과 오류율
- Refresh Token 및 대기열 저장소 변경에 따른 정합성과 I/O 비용

---

## 4. 프로젝트 원칙

1. 구현한 것과 계획한 것을 구분합니다.
2. 성능은 구조만으로 단정하지 않고 측정 결과로 설명합니다.
3. Gateway, Auth, 도메인 서비스의 책임을 섞지 않습니다.
4. 기술을 추가하기 전에 현재 구조의 실패 조건과 한계를 기록합니다.
5. 재현 가능한 실행 환경과 회귀 테스트를 기능 구현의 일부로 취급합니다.
